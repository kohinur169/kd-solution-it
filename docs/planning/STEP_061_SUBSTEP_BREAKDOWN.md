# STEP 061 - Sub-step breakdown

STEP 061: **File upload validator with magic byte and size checks** (`docs/final/STEP_PLAN_250.md`
line 800), from `docs/final/FEATURE_LIST.md` lines 225-229 ("Every file is AES-256-GCM encrypted before
upload", "File type and magic byte verification and file size limits apply", "KYC documents, logos,
invoice PDFs, dispute documents and support attachments can be uploaded") and rule 11 of
`docs/final/MASTER_PROMPT.md`.

## What already exists, and what is missing

Migration `0057_files.sql` (STEP 031) already defines the contract, and it is stricter than any validator
would invent on its own:

- five purposes: `kyc_document`, `company_logo`, `invoice_pdf`, `dispute_document`, `support_attachment`;
- `byte_size between 1 and 52428800`, `content_type ~ '^[a-z]+/[A-Za-z0-9.+-]+$'`, `content_sha256` of
  64 hex characters;
- a state machine: `pending` with no verdict, `ready` or `archived` only with `magic_byte_verified` and
  `verified_at`, `quarantined` with a reason of 1 to 280 trimmed characters that is never rewritten.

What does not exist is the code that produces those facts. Nothing in the platform reads a file's bytes:
the KYC screens of sections 79-99, the logo upload of section 12 and the dispute documents of section 191
all arrive later, and each of them would have written its own `content_type.startsWith("image/")` check.

## The decisions this STEP makes

1. **The bytes decide the type, not the header.** The first 32 bytes are compared with four signatures -
   `%PDF-` (hyphen included), `FF D8 FF`, the eight byte PNG signature and `RIFF` + `WEBP` at offset 8.
   The `Content-Type` a client sends is a claim, and a handler that stores the claim and serves it back is
   a stored XSS with a download button.
2. **Signatures are matched at a fixed offset, never searched for.** A JPEG header at byte 1 is not a
   JPEG; a PNG header inside a document is a polyglot.
3. **Quarantine is not refusal.** A row with `magic_byte_verified = false` and a reason is evidence a
   person can read; a refusal discards it and turns a probe into a retry. So a claim that disagrees with
   the bytes is quarantined, while an empty file, an oversized file or an unacceptable type is refused
   with `422 VALIDATION_FAILED` - it never deserved a row.
4. **A quarantine carries its own reason, and the reason fits the column.** Three sentences, each under
   280 trimmed characters: unknown signature, type mismatch, and markup-or-script where a document was
   claimed.
5. **The name is cleaned, never trusted, and never used as a key.** `sanitizeFileName` from STEP 056
   removes a path segment, a NUL and a reserved device stem; the storage key is generated by the platform
   and must start with the merchant id, which `0057` already enforces with `files_tenant_path_check`.
6. **SVG and the archive formats are refused, with the reasons in the module.** An SVG is a document that
   can carry script and this repository has no SVG sanitiser; a ZIP container needs an extractor with its
   own bomb, traversal and macro rules and no purpose needs one.
7. **The limits are per purpose and all under the row check.** A logo is 2 MB because it is an icon; a
   KYC scan is the full 50 MB because it is a photograph of a utility bill; invoices are 25 MB and
   support attachments 10 MB. The gate proves every limit is at or under 52 428 800, which is the number
   the database will accept.
8. **The validator and the migration are asserted to agree.** The gate reads `0057_files.sql` and checks
   the purpose names, the size literal, the content type pattern and the reason length against the
   module's constants. A validator looser than its row fails an insert in production; one stricter than
   its row is a surprise.

## Sub-step 3 - Database

None, and deliberately so: `0057_files.sql` already carries the whole contract - the five purposes, the
50 MB row check, the content type pattern, the hash shape, the reason length and the state machine that
turns `magic_byte_verified` into `ready` or `quarantined`. Adding a second copy of the type allowlist as a
SQL constraint would be a second answer that drifts; the gate compares the module with the migration
instead, so the two are one statement.

## Sub-step 4 - The core logic

`lib/security/upload.ts`:

- `UPLOAD_PURPOSES`, `UploadPurpose` - the five names of `0057`;
- `UPLOAD_POLICIES` - allowed types and maximum bytes per purpose, frozen;
- `UPLOAD_DATABASE_MAXIMUM_BYTES` and `UPLOAD_MAXIMUM_REASON_LENGTH` - the two numbers the row checks use;
- `UPLOAD_SNIFF_BYTES`, `sniffHead(bytes)` - the first 32 bytes, which is all a decision needs;
- `detectContentType(head)` - fixed-offset signature matching for the four accepted types;
- `sha256Hex(bytes)` - the digest `files_hash_check` requires;
- `validateUpload(candidate, purpose)` - rejected, quarantined or verified;
- `UPLOAD_QUARANTINE_REASONS`, `uploadRejection(reason)`, `requireValidUpload(...)` - the vocabulary, the
  `422` and the call a route makes.

## Sub-step 5 - Routes and jobs

There is no route to connect yet, and the STEP is honest about it: no handler in this repository reads a
file. `app/` contains no `formData()` call and no upload endpoint; the file surfaces arrive with the
storage STEPs 100-105 (`lib/storage/`), the KYC STEPs 79-99 and the dispute STEPs 191-199, and each of
them owns its route. What this STEP leaves behind is the invariant those routes must satisfy - the gate
already holds the validator to the database contract, so a route that skips it cannot claim the contract
was unknown - plus the serving rule recorded in `lib/security/README.md`:
`content-disposition: attachment` and `nosniff` on everything served from storage.

## Sub-step 6 - UI

Not applicable: the validator is called by a route that does not exist yet, and every outcome it can
produce reaches an existing form through `422 VALIDATION_FAILED`, which the screens already render. No
screen gains a field, a string or a state, so there is nothing to check at either width.

## Sub-step 7 - Security proof

`checkUploadValidator()` and `checkUploadWiring()` in `lib/security/verify.ts`: the policy table (five
purposes, every type provable from bytes and matching the row's pattern, no SVG, every limit under the
row check, all frozen), the signature corpus (each type from its own bytes, `%PDF` without the hyphen,
a truncated signature, a signature at the wrong offset, a RIFF that is not WebP, empty input, markup),
the decision matrix (verified, quarantine for mismatch and for markup and for an unknown signature,
refusals for empty, oversized, missing type and unacceptable type, the exact-limit case, a signature at
the start of a long file), the digest vector, the reason lengths, the refusal factory and the throwing
wrapper, and the migration agreement.

Nine mutation controls, all caught: a wrong PNG byte, a mismatch marked verified, the size check removed,
the purpose allowlist removed, the signature searched anywhere, a reason longer than the column, a logo
limit above the row check, the name sanitiser bypassed and the WebP second part dropped.
