# STEP 175 — super_admin selects at most one active supplementary IDV vendor with manual fallback and processor-KYB gate

**Status: COMPLETED**

## STEP

- Number and title: STEP 175 — super_admin selects at most one active supplementary IDV vendor with manual fallback and processor-KYB gate.
- Category: Optional supplementary identity verification adapters (Jumio, Didit, Sumsub), STEPs 170-175. This STEP is the last of the five and the only one that changes anything: it decides which of the three vendors, if any, may run, it turns the platform's verification mode into a value the office and the merchant each read in their own words, and it closes the path by which a supplementary result could ever have been mistaken for a processor KYB verdict.
- Depends on: STEP 170 (`lib/kyc/adapters/supplementary-idv.ts` — the catalogue, `supplementaryIdvModeOf`, the configuration store with its status rules, `refuseProcessorKybWrite` and the audited `recordSupplementaryIdvProcessorWriteRefusal`), STEPs 171-173 (the three adapters, each with the activation test that makes a row `active`), STEP 174 (`lib/kyc/adapters/deliveries.ts` — the receiver that turns a delivery into an answer), STEPs 037-055 (`lib/auth/session.ts` — `requireAnyRole` and `hasSatisfiedTwoFactor`), STEP 008 (`lib/errors/app-error.ts` — `AppError` and the code catalogue, which has no dedicated step-up code so this STEP uses `PERMISSION_DENIED`), STEP 064 (`lib/security/encryption.ts` — the keyring STEP 170 seals a configuration with; this file never opens it) and STEPs 147-169 for the adapter conventions (documented vocabularies, a gate that runs with plain `node`, and no route or table of its own).

## Database

None, and none was needed to hold the rule. The rule lives in one place: `status` on a configuration row, which STEP 170's store already guards, and this STEP's one write is a version-guarded move from `active` to `retired`. Sub-step 3 of the plan says "the database part of this STEP if any"; this block is granted no schema exception, so the honest answer is none. A later STEP that owns `migrations/` will find the invariants it must carry written down in STEP 170's store: one row per `(company, vendor, environment)`, at most one `active` per `(company, environment)`, a version guard on every write, `credentialSealed` immovable, and no write at all to a retired row.

## Not Run / Open

- **No route and no screen component.** The service is what such a route calls, and `canWriteSupplementaryIdvSettings` is what the component asks before rendering the control. `app/` belongs to a STEP that owns it, so the desktop and mobile widths of sub-step 6 were not exercised here: there is no component to render. Whoever builds the screen must call `selectSupplementaryIdvVendor` and `selectManualSupplementaryIdv` and render `supplementaryIdvSettingsOf`, and must not decide the permission in the component.
- **No migration.** Sub-step 3 says "if any", and this block is granted no schema exception. The invariants a real table must carry are listed above and in STEP 170's store.
- **No step-up error code.** The catalogue has no dedicated code for "role satisfied, second factor missing", so the denial is `PERMISSION_DENIED`, the same code the session guards use, with a detail naming `actor.twoFactorSatisfied`. A future catalogue entry would be a better answer than reusing this one.
- **A stalled session stays visible rather than becoming `expired`.** STEP 170's forward-only recorder needs the vendor's reference, and a session that never reached the vendor has none; forcing one would write a reference no vendor issued. When a poller exists, a stalled session with a reference should be read from the vendor and recorded as `expired`, which is the delivery receiver's path already.
- **Selection cannot activate a row.** A vendor whose credentials have not passed its own activation test cannot be selected, so the screen's first step is always "configure, test, activate", then "select". That is deliberate: a selection is a choice between proven vendors, not a proof.
- **The store is in memory.** `InMemorySupplementaryIdvConfigStore` carries the rules, not the durability; the database is a later STEP's work.
- **The store does not guard `webhookSecretSealed`.** STEP 170's `save` refuses a move of `credentialSealed` but not of `webhookSecretSealed`; this file never writes either column, and the gate proves both are byte-identical after a retirement, but a real table's trigger should refuse both.
- **No vendor is called and nothing is scheduled.** Turning "the selected vendor" into a session remains STEP 170's port and STEPs 171-173's adapters, and hearing a result remains STEP 174's receiver; this STEP only decides whether either may run.
