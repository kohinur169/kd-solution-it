## Database

None, and no migration number was consumed. Two store ports carry the invariants the tables must repeat, with in-memory reference implementations.

`SupplementaryIdvSessionStore`: a unique row id, a unique vendor reference per company and vendor, a new row that starts `in_progress` or `unknown` and nothing else, an immutable company, vendor, mode, configuration and creation snapshot, a session start time that never moves, the processor's status recorded as an immutable **snapshot**, a vendor reference that is written once and never replaced, a version guard, and forward-only results through `SUPPLEMENTARY_IDV_RESULT_MOVES` — a recorded `passed` never becomes `failed` or `expired`, and a recorded `failed` never becomes a pass.

`SupplementaryIdvConfigStore`: a new configuration must be `pending_activation`, a configuration never changes company, vendor or environment, a credential ciphertext never changes in place (a rotation is a new row), a retired configuration never comes back, and a stale version is refused.

The tables, their unique keys and their RLS belong to the STEP that persists them; no schema was claimed here.

## Behaviour Proof (acceptance checklist)

- **One port, three vendors, and nothing else on it.** `SupplementaryIdvAdapter` has exactly three members — `vendorKey`, `createSession`, `readSession` — and `isSupplementaryIdvAdapter` refuses an object that adds a fourth, so a vendor adapter cannot grow a processor-status writer. The gate proves the three-member fixture satisfies the port, that an object with an extra `writeProcessorStatus` does not, that a payment provider's key is not an IDV key, and that null or a bare string is not an adapter.
- **The two vocabularies share no word, which is the separation in executable form.** The supplementary results are `in_progress`, `passed`, `failed`, `expired`, `unknown`; the processor's five are `pending`, `action_required`, `verified`, `restricted`, `rejected`. `supplementaryIdvVocabularyIsDisjoint()` evaluates at module load, a pass is deliberately called `passed` and never `verified`, and a failure is never `rejected`. Feeding a processor word to the supplementary side is refused **by name** — `verified is a processor KYB status, so it is not a supplementary result` — and the gate drives all five through both `validateSupplementaryIdvVendorAnswer` and `recordSupplementaryIdvAnswer`, then asserts the session did not move and no second audit entry was written.
- **A KYB verdict is never written from here.** `refuseProcessorKybWrite` refuses every candidate: for one of the five words it names the word and says only the processor adapter may record it; for anything else it says a supplementary check never writes a processor status at all. `recordSupplementaryIdvProcessorWriteRefusal` audits the attempt itself, and an attempt against no session is refused without writing a row — so a future caller cannot turn a Jumio pass into `verified` silently.
- **The evidence is evidence.** `supplementaryIdvEvidenceOf` carries `processorKybAuthority: "processor"`, `changesProcessorKyb: false` and `requiresHumanDecision: true`, and the gate asserts its key list has no `processorStatus`, no `kybStatus`, no `chargesEnabled` and no `payoutsEnabled`. `SUPPLEMENTARY_IDV_DECISION_AUTHORITY` is `human_reviewer`: a person decides, because a supplementary check answers whether the applicant is who they say, not whether the platform may charge.
- **A session holds no personal data.** The record stores the vendor key, the mode, the configuration, the vendor's opaque reference, three result words, the document **kind**, a neutral reason code, the processor snapshot, the fallback and its timestamps — and the gate asserts the exact key list, then asserts that name, date of birth, document number, address, email, phone, image, selfie, vendor payload and credential are all absent. A document number or a face never enters this platform through this module.
- **An unhappy or unreadable check is a manual review, not a rejection.** A `failed` or `expired` answer sets `requiresHumanReview` and a fallback of `{ mode: "manual", merchantVisible: false }`, and the audit records both the result and the fallback. An `in_progress` answer moves nothing else. That is the feature list's own rule — an incomplete or unsuccessful automatic check moves to manual review.
- **The merchant sees one neutral phrase.** `supplementaryIdvMerchantStatusOf` maps the results to `verification_in_progress`, `verification_complete` and `verification_incomplete`. For every result the gate checks the phrase against all three vendor labels, all three vendor keys, all eight reason codes, and the words "processor" and "kyb": none of them may appear. The merchant never learns which method ran or why it stopped.
- **Manual KYC is the running mode.** `supplementaryIdvModeOf` answers `manual` for no configuration, for a waiting one and for a retired one, `automatic` with the vendor's key when exactly one is active, and — the case that matters — `manual` with a reason naming the defect when **two** are active, because a configuration error is not repaired by choosing a vendor at random. `validateSupplementaryIdvConfigs` refuses two active vendors per company, the same vendor active twice, and an unknown vendor key, while two different companies may each have one.
- **Credentials are sealed per vendor, per company and per purpose.** `sealSupplementaryIdvConfig` refuses an empty, padded, whitespace-bearing or oversized credential before sealing, and both secrets are sealed under their own AAD scopes. The gate then proves the scopes matter: a Jumio credential does not open for Didit, one company's credential does not open for another company, a delivery secret does not open as a credential, and another keyring opens nothing. `validateSupplementaryIdvCredential` keeps the platform's 8 KiB bound.
- **UI** — not applicable: this STEP adds no screen, so no desktop or mobile width was checked. The vendor settings screen belongs to STEP 175 and the merchant's own status line reads the neutral phrase above; a screen is not part of an interface STEP.
- **Security** — no secret, token or personal datum is stored in a record or an audit entry; every audit entry carries `officeOnly: true`, the provider's vendor key, the company, the session, the result, the neutral reason and the time, and the gate asserts no entry stringifies to contain the credential, the delivery secret or the vendor reference; every state transition is version-guarded and forward-only; the six audit actions are the module's whole vocabulary; and no route, job or table is added, so the pre-existing RLS and permission middleware are untouched.

## Not Run / Open

- **No vendor is implemented, and no vendor page was read in this STEP.** The provider documentation rule applies when an adapter for Jumio, Didit or Sumsub is written; STEPs 171-173 read those pages in their own sessions and translate their payloads into `SupplementaryIdvVendorAnswer`. This STEP could not map a vendor's raw statuses without inventing them, so it maps nothing.
- **This gate is not in the `verify` chain.** `package.json` is a shared file the File Ownership Rules give to the foundation STEPs, and no exception is granted to STEPs 170-175 (the KYC STEPs 079-099 left their checks out of it for the same reason). Running it needs `node lib/kyc/adapters/supplementary-idv-verify.ts`; adding it to `verify` is a one-line change for whoever owns `package.json`.
- **Nothing is persisted, routed or shown.** Both stores are ports with in-memory reference implementations; the session and configuration tables, their RLS policies, the vendor settings screen (STEP 175), the session-opening API and the webhook receiver (STEP 174) arrive with the STEPs that own them.
- **Manual KYC remains the running mode.** No configuration is active anywhere, so `supplementaryIdvModeOf` answers `manual` for every company today, which is the feature list's stated starting state.
- **The processor snapshot is only a snapshot.** This module records what the processor's own adapter reported at the time; it never reads the processor, and the two records are reconciled by the reviewer, not by this file.
