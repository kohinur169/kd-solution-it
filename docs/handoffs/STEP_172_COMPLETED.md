## Behaviour Proof (acceptance checklist)

- **One host, two calls, and the account host refused by name.** `DIDIT_ALLOWED_CALLS` is exactly `POST /v3/session/` and `GET /v3/session/{uuid}/decision/`; `diditFetchTransport` throws before it builds a request for anything else. The gate proves both are allowed and refuses the update-status `PATCH`, the session `DELETE`, the `generate-pdf` read, the session list, a workflow create, the `apx.didit.me` account surface, a non-UUID decision path, a traversal path and a missing trailing slash — then asserts the source names no host but Didit's and never calls the account host.
- **The key travels in one header and nowhere else.** There is no OAuth exchange to cache; every call carries `x-api-key` from the sealed configuration, the transport refuses to run without it, and the gate asserts no call carries a query string, no path carries the key, no request body carries it, and no audit entry or stored row contains it.
- **The mode is declared, never inferred.** Didit documents that a key may be `sk_live_`, `sk_test_` or carry no prefix at all and still work. `diditKeyPrefixOf` records the prefix for the office view, and the gate proves that all three key shapes validate and that no code path turns a prefix into a mode.
- **Activation creates nothing billable.** `activateDiditConfiguration` reads the decision of a random UUID: `404` means the key authenticated and Didit simply does not know that session, and that is what activates the row; `401`, `403`, `429`, `5XX`, a throw or a redirect leaves it `pending_activation`. The gate proves every one of those, and that the probe is a `GET` with no body.
- **A session row exists before Didit is called, and a retry reconciles.** `openDiditSession` refuses an unknown session, another vendor's session, a finished one, one that already carries a reference (with no call made), a configuration that is not active, one sealed under another keyring, a session and configuration that disagree about the mode, and a request whose workflow is not a UUID — then calls Didit and records the reference through STEP 170. A `500` or `429` records nothing and reports `requiresReconciliation`, and the gate proves the **retry sends the same `vendor_data`**, which is what makes Didit's documented one-unfinished-session rule return the same session instead of a second one.
- **The hosted URL carries a session token, so it is never stored.** `DiditOpenedSession.redirectUrl` is answered once; the gate asserts the stored row contains no hosted URL, no hosted token and no key, and that the reference — Didit's session id — is all that is kept.
- **The exact spaced statuses are the vocabulary.** The ten session strings and the five feature strings are frozen verbatim, spacing and case included. The reader takes them **without trimming**, and the gate proves that `"Approved "` with a trailing space, `"approved"` in lower case and `"VERIFIED"` all become `unknown` rather than a pass.
- **Mapping, and why each word lands where it does.** `Approved` passes; `Declined` fails; `In Review` is `unknown` because Didit itself says a reviewer decides; `Expired`, `Abandoned` and `Kyc Expired` are `expired` because the session ended without an answer; `Not Started`, `In Progress`, `Awaiting User` and `Resubmitted` are `in_progress` because a person still has work to do. The reason comes from a documented warning risk first (`DOCUMENT_EXPIRED`, `LIVENESS_FACE_ATTACK`, `NO_FACE_DETECTED`, `LOW_LIVENESS_SCORE`, `LOW_FACE_MATCH_SIMILARITY`, `NO_REFERENCE_IMAGE`), otherwise from the feature that decided — a declined document is `document_unreadable`, a declined face match is `document_mismatch`, a declined liveness is `liveness_failed`. The gate drives thirty-one decision shapes through it.
- **A business session is never a person's result.** Create answers `session_kind` and the decision carries it, so both are branched on: a `business` session produces `unknown` even when its status says `Approved`, and the create answer refuses a business kind outright.
- **A recorded pass is not rewritten by a later expiry.** A `Kyc Expired` decision on a row already recorded `passed` is **refused** by STEP 170's forward-only recorder, and the gate asserts the pass still stands — a document that expired after approval is a reason for a new session, not for editing an old result.
- **A document class maps to a neutral kind, and no further.** `Passport`, `Identity Card`, `Driver's License` and `Residence Permit` map to their neutral kinds; a visa, a health card, a tax card, an unsupported class or a class this file has never read stay `not_stated`, because the neutral vocabulary has no word for them and a claim the record cannot support is worse than none.
- **No personal data crosses either way.** The create body carries four fields — `workflow_id`, `vendor_data`, `callback`, `callback_method` — and the gate asserts no name, date of birth, document number, `expected_details`, `contact_details`, `portrait_image`, `metadata` or `sandbox_scenario` is sent; the stored row and the audit entries carry none of Didit's `document_number`, `first_name`, `last_name`, `date_of_birth` or media URLs even though the decision body in the gate contains all of them.
- **A supplementary pass is never a KYB verdict.** Every answer is one of STEP 170's five words; the gate asserts for every shape that the result is not one of the processor's `pending`, `action_required`, `verified`, `restricted`, `rejected`, that `supplementaryIdvOverlapsProcessorKyb` is false, that `refuseProcessorKybWrite` refuses at the boundary, that the office summary carries `changesProcessorKyb: false`, and that the merchant phrase names neither the vendor nor its word `Declined`.
- **UI** — not applicable: this STEP adds no screen, so no desktop or mobile width was checked. The vendor settings screen is STEP 175's.
- **Security** — the key and the delivery secret exist only inside the sealed field and the one header; every answer is bounded by `DIDIT_MAXIMUM_ANSWER_BYTES`; redirects are refused; the timeout is bounded; the vendor's own problem detail is bounded and stored nowhere; and no route, job or table is added, so the pre-existing RLS and permission middleware are untouched.

## Not Run / Open

- **No delivery receiver, and no signature verifier.** Didit's webhooks sign with `X-Signature-V2` over `X-Timestamp` and the raw body; that receiver is STEP 174's and is **not** implemented here. This file never trusts a delivery: it reads the canonical decision, which is what a delivery would have to be confirmed against.
- **No vendor settings screen.** The screen that saves, activates, rotates and retires a Didit configuration is STEP 175's; this STEP supplies `createDiditConfiguration` and `activateDiditConfiguration` and their audit vocabulary.
- **`docs/final/PROVIDER_DOCS.md` was not touched.** It belongs to STEPs 147-169 and this STEP owns `lib/kyc/adapters/`; the provider facts live in the adapter's header table and in the section above, ready to lift across unchanged by whoever owns that file.
- **This gate is not in the `verify` chain.** `package.json` is a shared file the File Ownership Rules give to the foundation STEPs, and no exception is granted to STEPs 170-175. Running it needs `node lib/kyc/adapters/didit-verify.ts`.
- **Sandbox runs on the same host.** Didit documents no separate test host: a sandbox run is an application whose key carries the `sk_test_` prefix (or a key created before the prefix existed), with 500 test sessions per 24 hours and `sandbox_scenario` to force an outcome. This adapter deliberately does not send `sandbox_scenario`, because the scenario would have to come from a caller and would let a production flow choose its own verdict; the mode is declared on the configuration instead.
- **No document, image or expected detail is ever sent.** The person is handed to Didit's hosted page; document images, `expected_details`, `contact_details` and prepared data are deliberately not implemented, so no name, date of birth, document number or face enters this platform through this module, and the decision's OCR fields are discarded apart from the document *class*.
- **Nothing is persisted, routed or shown.** Both stores are STEP 170's ports with in-memory reference implementations; the tables, their RLS, the session-opening route and the refresh job arrive with the STEPs that own them.
- **Manual KYC remains the running mode.** No configuration is active anywhere, so STEP 170's `supplementaryIdvModeOf` still answers `manual` for every company today.
