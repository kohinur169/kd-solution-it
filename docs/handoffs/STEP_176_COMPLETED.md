## Provider documentation read in this session

Every fact in `lib/tax/taxcloud.ts` traces to one of these pages, read before the file was written. The v3 documentation index (`https://docs.taxcloud.com/api-v-3/llms.txt`) was used to find the endpoint pages, and the migration page established which generation this platform must speak.

| Page | What it established |
|---|---|
| https://docs.taxcloud.com/guides/getting-started/setup-and-authentication | A key is generated under Developer > API and sent in `X-API-KEY`; v3 also accepts a JWT in `Authorization: Bearer` but the guide says to use `X-API-KEY`; the `connectionID` is a UUID in the URL path and "has replaced `API Login ID` in all endpoints"; a Ping answers `401` for a wrong key and `404` for a mistyped or someone else's connection; "TaxCloud does not provide a separate sandbox environment", and two connections are the documented way to keep test and live apart. |
| https://docs.taxcloud.com/guides/getting-started/testing-and-going-live | Same base URLs and endpoints in development, testing and production; credentials and connection ID work in both modes; "the `connectionID` in your request determines which environment you're working in"; once a connection is live, every order, exemption and completion is treated as real and included in reporting; certificates and settings do not transfer between connections. |
| https://docs.taxcloud.com/guides/getting-started/how-tax-cloud-works | The minimum integration is VerifyAddress, Lookup, order completion and returns, in that order; the Lookup family returns tax amounts and not jurisdiction detail, because rates would require developers to do their own rounding, caps and thresholds. |
| https://docs.taxcloud.com/guides/getting-started/migrating-from-api-v-1-to-v-3 | v1 was SOAP/XML or JSON over `api.taxcloud.net/1.0/TaxCloud/{method}` with `apiLoginID` and `apiKey` **in the body** and PascalCase fields; v3 is REST/JSON over `api.v3.taxcloud.com/tax/connections/{connectionId}/...` with `X-API-KEY` and camelCase fields; `Lookup` became `POST /carts`; `Authorized`/`Captured`/`AuthorizedWithCapture` became `POST /carts/orders`; `Returned` became `POST /orders/refunds/{orderId}`; `ResponseType` became HTTP status codes; v3 returns the rate beside the amount. |
| https://docs.taxcloud.com/api-reference/api-reference/sales-tax-api/cart/create-cart | `POST /tax/connections/{connectionId}/carts` takes `items[].{customerId,currency,origin,destination,lineItems}` and is an **UPSERT on `cartId`**; the response carries `tax.{amount,rate}` per line item; the documented errors are `400`, `401`, `403`, `404`, `422`, `429` and `500` with a problem body of `title`, `detail`, `status`, `type`, `instance` and `errors[{location,message,value}]`. |
| https://docs.taxcloud.com/api-reference/api-reference/sales-tax-api/utilities/ping | `GET /tax/connections/{connectionId}/ping` verifies authentication for that connection and answers `200` with `message`; `401` means the `X-API-KEY` header is wrong and `404` means the connection ID is mistyped or belongs to another account. |
| https://docs.taxcloud.com/api-reference/api-reference/sales-tax-api/health | `GET /tax/health` answers an overall `status` plus `components[{status,type}]`, takes no connection ID and proves nothing about a merchant's credentials. |
| https://docs.taxcloud.com/guides/workflows/real-time-api/convert-carts-to-orders | `POST /tax/connections/{connectionId}/carts/orders` takes `orderId`, `cartId` and `completed` and answers `201`; `orderId` must be unique per connection; `completed: true` finalises the order into the tax liability; `completedDate` in the body (or a later `PATCH /orders/{orderId}`) completes it and a **future** `completedDate` is rejected with `422`; "Orders that have no `completedDate` are not included in tax filings". |
| https://docs.taxcloud.com/api-reference/api-reference/sales-tax-api/orders/create-order | `POST /tax/connections/{connectionId}/orders` uploads an order that never had a cart: `transactionDate`, `completedDate`, `customerId`, `currency`, `origin`, `destination`, `lineItems` required; `kind` is `order` or `credit`; `excludeFromFiling` omits it from the filed return; `exemption` carries `isExempt` and `exemptionId`; `addressAutocomplete` may be `none`, `origin`, `destination` or `all`. |
| https://docs.taxcloud.com/api-reference/api-reference/sales-tax-api/orders/get-order | `GET /tax/connections/{connectionId}/orders/{orderId}` answers the stored order and expands `refunds` with `expand=refunds`; this is how state is read back, because no page read here documents a push. |
| https://docs.taxcloud.com/api-reference/api-reference/sales-tax-api/cart/get-cart | `GET /tax/connections/{connectionId}/carts/{cartId}` answers the stored cart with its line items and their tax. |
| https://docs.taxcloud.com/api-reference/api-reference/sales-tax-api/utilities/verify-address | `POST /tax/verify-address` takes `line1`, `city`, `state`, `zip` and a `countryCode` whose "default and only currently accepted value is US", truncates lines longer than 50 characters and returns the corrected address. |
| https://docs.taxcloud.com/api-reference/api-reference/sales-tax-api/refunds/refund-order | `POST /tax/connections/{connectionId}/orders/refunds/{orderId}` creates a refund; several are allowed while the refunded quantity never exceeds the ordered one; "Refund prices and tax amounts are automatically calculated from the order ... Do not send price or tax fields"; an optional `idempotencyKey` makes a retry return the original refund with `200`, and omitting it answers an `X-TaxCloud-Warning` header recommending one; `returnedDate` defaults to now and a prior-month date may trigger an amended filing. |
| https://docs.taxcloud.com/guides/core-concepts/managing-tax-exemptions | Certificates are customer-level and belong to one connection; `POST /tax/connections/{connectionId}/exemption-certificates` takes `customerId`, `customerName`, `address`, `customerBusinessType`, `reason`, `reasonDescription` and `states`; direct attachment by `exemptionId` is recommended over auto-match; an exempt order with no matched certificate is "still marked as exempt, but no certificate will be associated", leaving a filing gap; disabling a certificate never deletes it and existing orders keep their exemption. |
| https://docs.taxcloud.com/guides/core-concepts/components-of-tax-calculation | Tax depends on origin, destination, nexus and jurisdictions, the TIC and any exemption; without nexus in a state the API "will return a tax rate of 0% ... and still record the order data to track toward the state's economic nexus thresholds". |
| https://docs.taxcloud.com/guides/workflows/handling-errors | `400` is a body that does not match the schema (a missing required field, "`price` as a string instead of a number", unsupported fields), `422` is a well-formed body with unusable contents (an incomplete address, an exempt order with no exemption), `500` is "a temporary issue on TaxCloud's end" for which the page prescribes exponential backoff, and the page asks for every response to be logged. |
| https://docs.taxcloud.com/guides/core-concepts/tic-search | Every product needs a TIC and a wrong TIC is wrong tax; `POST /tax/tic/search` takes `query` (non-empty), `limit` (1-100, default 10) and `cursor` and answers ranked results with `ticId`, `label`, `description` and a `0`-`1` score; documented errors are `INVALID_QUERY` and `INVALID_LIMIT` (`400`), `RATE_LIMIT_EXCEEDED` (`429`), `INTERNAL_ERROR` (`500`) and `503` for the search service with a `Retry-After` header to honour. |

The v1 documentation index (`https://docs.taxcloud.com/api-v-1/llms.txt`) was read only to confirm that v1 is still published and is **not** what this platform speaks; the v1 hosts are refused by name in the record.

## Not Run / Open

- **No HTTP client.** This STEP builds a request as a value and sends nothing; STEP 177 is the one that performs the ping, and it must send the request this builder produced rather than assemble its own.
- **No sealing and no key handling.** `apiKeySealed` is named, not written; STEP 177 seals with STEP 064's keyring and this record's masking function is what a screen shows afterwards.
- **No route and no screen.** `app/` is not this STEP's, so the desktop and mobile widths of sub-step 6 were not exercised: there is no component. The connect screen belongs to STEP 177, which owns the tax settings surfaces.
- **No migration.** This block has no schema exception; the invariants a table must hold are written down in `taxCloudConnectionProblemOf` and in the Database section above.
- **The word "sandbox" is deliberately absent.** TaxCloud documents no sandbox host, and a merchant typing "sandbox" is offered a test connection instead; if TaxCloud ever publishes one, this record's `TAXCLOUD_SANDBOX_BASE` is the single place that changes.
- **v1 is not implemented and never will be here.** The refused hosts are named so a misconfiguration is a refusal rather than a v1 request to a v3 endpoint, and the migration table in the sources is what a future reader uses to see why.
- **Rate limits and timeouts are unknown.** `429` is documented and `Retry-After` only on the TIC search `503`, so the client STEP 179 writes must honour `Retry-After` when it appears, back off otherwise, and apply its own timeout rather than claiming a documented one.
- **No push.** No page read here documents a callback or webhook, so order and refund state is read back with `GET /orders/{orderId}` (and `expand=refunds`); a poller is the design, not a hope.
- **TIC assignment is merchant work.** The record can search TICs, but which TIC a product deserves is a decision the merchant makes; STEP 179 must use the general code `0` only as the documented fallback and never as a guess dressed as a classification.
