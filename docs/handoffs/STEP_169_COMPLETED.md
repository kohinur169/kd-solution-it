## Behaviour Proof (acceptance checklist)

- **A payout is booked only for an account that can receive one.** `bookAirwallexPayout` checks STEP 167's readiness first: a `SUBMITTED`, `ACTION_REQUIRED`, `SUSPENDED`, rejected, unknown or never-created account is refused with the mapping's own sentence, an account belonging to another company is refused by name, and a company with no active configuration books nothing — none of those writes a row or makes a call. The request is then validated: a zero or negative amount, a currency other than USD, a malformed or `acct_` beneficiary id, a blank, over-long or credential-shaped reference are each refused with their own reason.
- **Booking is the platform's decision, and it is recorded as exactly that.** The row is written with `outcome: null`, `transferId: null`, `provisional: false` and `final: false`, under the documented `request_id` derived from the company and the reference and namespaced `payout|` so it can never collide with a payment's. `airwallexPayoutLedgerOutcome` then answers `none` with the reason (`no provider transfer id yet`), so nothing can be debited on the strength of a booking. A second booking with the same reference answers `already_booked` with the first row, and writes no second audit entry.
- **The two create bodies are refused rather than guessed.** STEP 165 recorded the transfer and beneficiary paths and never read either request body's field names, so `createAirwallexTransfer` and `createAirwallexBeneficiary` answer `unsupported` naming the unread page, and the create path is **not** on `AIRWALLEX_PAYOUT_ALLOWED_PATH_PATTERNS` — the gate asserts that it is not callable, that a traversal and a short id are not callable, and that the bare prefix is not a read. The transport refuses an unallowlisted path, an empty token, an empty API version, an `x-on-behalf-of` that does not name a connected account, and a short id — all before any socket is opened.
- **The transfer id proves existence, never status.** `attachAirwallexTransferId` accepts one bounded id (and refuses an `acct_` id by name), writes it once, refuses a second different id and refuses to attach to a final payout; the outcome stays `null` until a read or a delivery reports one, and the ledger still says `none` afterwards.
- **A read is accepted only for the id that was asked about.** `readAirwallexTransfer` sends a GET to the id-shaped path with the cached token, the pinned version and the acting account, and `parseAirwallexTransferReadAnswer` maps the documented classes: `2XX` with a recorded status is a read, `404` is `not_found`, `400`/`401`/`403` are failures, and a redirect, a timeout class, `429`, a `5XX` or a thrown transport leave the status unread. An answer naming another transfer id is refused, and an undocumented status is never `paid` — the gate drives all eleven statuses and eight answer classes through it.
- **`PAID` is provisional, and the outcome table is what keeps it honest.** Applying a status uses STEP 165's transfer mapping unchanged: `PAID` → `paid` with `provisional: true` and `final: false`; `FAILED` and `CANCELLED` → final; the approval, scheduled, overdue, processing and sent states → `in_flight`, not final; an unrecorded status → `unknown` with `requiresReconciliation` and the status named in the row. `paid → failed` is allowed because the page says a paid transfer may still fail; `paid → in_flight`, `failed → paid` and a repeat of the status already held are refused, so a stale read cannot walk a settled payout backwards. The gate proves the whole path: paid, then a later `FAILED`, and the ledger is told the failure is final.
- **Only the platform's own window makes a paid payout final.** `closeAirwallexPayoutWindow` refuses anything that is not `paid` and still provisional, and when it does run it records `final: true`, `provisional: false` and the close time — the window's length is STEP 141's policy, not an Airwallex number. A failure arriving after the close is refused rather than absorbed, so a late reversal reaches a person instead of moving final money.
- **The delivery is verified before it is parsed.** `receiveAirwallexWebhook` checks size, then the company's active configuration, then opens that company's sealed secret with the keyring using STEP 166's scope, then verifies `x-signature` over `x-timestamp` plus the raw body with STEP 165's verifier, and only then parses **the same string** — no re-serialised JSON. A delivery signed with another company's secret, a body changed after signing, an upper-case digest, a missing timestamp, a non-Unix timestamp, a delivery 900 seconds stale, an empty body, an oversized body, an unparseable body and an envelope without an `evt_` id are each refused, and none of them writes a row.
- **A retry applies nothing.** The documented `evt_` id is the dedupe key: the first delivery is recorded and applied, every later one answers `duplicate` with `200` and changes nothing — including a replay of the same event id carrying a different body, whose digest is not allowed to overwrite the first. The record keeps a SHA-256 digest of the body and never the body; the gate asserts the record's key list.
- **What an event means is STEP 165's vocabulary, not a guess.** A payment intent event is read through the Intent mapping (`SUCCEEDED` is the only `paid`, `CANCELLED` is a failure, an object with no status is `unknown`), a payment attempt event is evidence with its own name and never an Intent status, and a transfer event takes the object's status when it is documented and otherwise derives it from one of the eleven recorded names — with `PAID` again `paid` and provisional. An event name the record does not subscribe to is acknowledged and recorded as `ignored`, and the account event group is empty, so the gate proves that `account.updated` and `account.status_changed` have no effect and no account name is subscribed.
- **The answer is the page's.** `airwallexWebhookResponseOf` answers `200` for applied, ignored and duplicate, `401` for an unverified delivery, `400` for one that will never parse, and `500` **only** when the platform could not record the work — the one case where the provider's retry helps, which the gate proves by making the store throw on insert and return false on save. No answer carries the body, the secret, the signature or the token.
- **UI** — not applicable: this STEP adds no screen, so no desktop or mobile width was checked. A payout screen and the webhook route that mounts this receiver arrive with the STEPs that own `app/`; a screen is not part of an adapter STEP.
- **Security** — the access token and the webhook secret are opened per call and never stored in a record; the delivery record keeps a digest instead of the body; the audit vocabularies name ten actions (`airwallex_payout.booked`, `.transfer_attached`, `.status_read`, `.failed`, `.closed`; `airwallex_webhook.received`, `.duplicate`, `.refused`, `.ignored`, `.failed`) carrying the provider key, the company, the payout or event, the transfer id, the mode, the outcome and the time; the gate asserts no audit entry and no record stringifies to contain the token, the API key, the secret or the signature; every provider message is sanitised and bounded; and the amount arithmetic stays in the platform's integer minor units. No route, no job and no table, so the pre-existing RLS and permission middleware are untouched.

All four payout/delivery sandbox rows stay `Not run`, `AIRWALLEX_SESSION_STATUS` stays `partial`, and the record can never say `verified` — the capability matrix now closes with that status because this is the provider's last STEP.
- **The transfer create body is still unread, so this adapter never starts a transfer.** The path, the eleven statuses and `PAID`'s late failure are recorded; the request body's field names are not. `createAirwallexTransfer` answers `unsupported` by name and the create path is not on the allowlist, so the payout is booked here and the transfer id attached when the surface that created it reports it. Reading `docs/airwallex/transfers/create-a-transfer` is the one task that turns this refusal into a call, and the gate that asserts the refusal must then be changed deliberately.
- **The beneficiary create body is unread for the same reason.** `POST /api/v1/beneficiaries/create` is recorded and not callable; registering a beneficiary remains outside this adapter.
- **The account-status event names were never read**, so no account event is subscribed and the receiver has no account branch. The subscription review sees exactly the twenty-four names STEP 165 recorded.
- **The settlement window's length is STEP 141's policy, not a provider number.** This STEP exposes `closeAirwallexPayoutWindow` and refuses to close anything that is not paid and still provisional; when the ledger should call it is decided where the settlement policy lives.
- **Persistence, the route and the screen are later work.** Both stores are ports with in-memory reference implementations; the tables, their RLS policies, the payout route, the webhook route that mounts this receiver and the payout screen arrive with the STEPs that need them, and none is claimed here.
- **The category closes here.** STEP 169 is the last of the five payment-provider adapter STEPs (147-169); every provider's sandbox record is `partial` for the same reason — no live credential exists in this environment.
