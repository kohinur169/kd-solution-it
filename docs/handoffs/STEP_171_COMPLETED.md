# STEP 171 — Jumio supplementary identity/liveness adapter with encrypted configuration and verification session

**Status: COMPLETED**

## STEP

- Number and title: STEP 171 — Jumio supplementary identity/liveness adapter with encrypted configuration and verification session.
- Category: Optional supplementary identity verification adapters (Jumio, Didit, Sumsub), STEPs 170-175. This is the first vendor under the port STEP 170 defined: 170 owns the neutral vocabulary, this STEP reads Jumio's own pages and translates Jumio's words into `SupplementaryIdvVendorAnswer`. 172 (Didit) and 173 (Sumsub) do the same behind the same three members, 174 verifies the deliveries these vendors send, and 175 lets a super administrator activate at most one of them.
- Depends on: STEP 170 (`lib/kyc/adapters/supplementary-idv.ts` — the port, the vocabulary, the sealed configuration, the session store and the forward-only recording function; `lib/kyc/adapters/supplementary-idv-verify.ts` — the gate this file's gate imitates), STEP 056 (`lib/security/encryption.ts` — the AES-256-GCM keyring both seals and opens the configuration and the delivery secret), and STEPs 147-169 for the adapter conventions (an allowlisted surface, a transport port, bracketed HTTP classes, and a gate that runs with plain `node`).

## Behaviour Proof (acceptance checklist)

- **Only three documented calls are reachable.** `JUMIO_ALLOWED_CALLS` is exactly `POST /oauth2/token` on the auth host, `POST /api/v1/accounts` on the account host, and `GET /api/v1/accounts/{uuid}/workflow-executions/{uuid}` on the retrieval host; `jumioFetchTransport` throws before it builds a request for anything else. The gate proves the three are allowed and refuses a `PUT` on the account path, a credential upload path, the `DELETE` wipe, the `/generate` PDF, the `/status` shortcut, the uptime `status.*` host, a traversal path and a rewritten path — then asserts that the transport itself refuses an account path on the token host, basic authentication on the account host, and an API call with no token.
- **The token is reused, as Jumio's own page asks.** `jumioAccessTokenFor` reads the cache first and only asks `POST /oauth2/token` when the cached token would expire within `JUMIO_TOKEN_REFRESH_SKEW_SECONDS`. The gate opens two sessions on one cache and asserts the second open makes **one** call, and that the call is the account call.
- **The configuration is sealed, and inert until it is proved.** `createJumioConfiguration` validates the datacenter and both credential halves before sealing, stores the row `pending_activation`, and returns the configuration with no plaintext in it; the gate asserts the stored row contains neither the client id nor the secret and that both ciphertexts are envelopes under different purposes. `activateJumioConfiguration` opens the credential, asks for a real token, and only a token answer moves the row `active` with the version bumped; a `401` leaves it waiting. The gate proves a refusal does not activate, that a second configuration in the same company and mode is refused **before any vendor call**, and that another company — and the same company in the other mode — may each have their own active configuration.
- **A session row exists before Jumio is called.** `openJumioSession` refuses an unknown session, another vendor's session, a session that is no longer `in_progress`, a session that already carries a reference (with no call made at all), a configuration that is not active, a configuration sealed under another keyring, and an unusable request — then calls Jumio and records the reference through STEP 170's `recordSupplementaryIdvAnswer`. The gate asserts a rejected request, a `500`, a `429`, a redirect, a duplicate `409` and an unreachable account endpoint never produce a recorded result, and that an unclear answer reports `requiresReconciliation: true` rather than inventing one.
- **A redirect URL is answered once and never stored.** `web.href` carries an `authorizationToken` in its query string, so `JumioOpenedSession.redirectUrl` is returned to the caller and is not part of the session row: the gate asserts the stored row contains no `authorizationToken`, no redirect URL, no credential, and only the reference. The audit entries are checked the same way, and the transport calls are asserted to carry no query string at all.
- **Only the status the documentation shows is believed.** `workflow.status` is a free string in the specification, so this adapter has no status table: `PROCESSED` is the one status carrying decisions, anything else is `in_progress`, and the capture client's documented `expired` state is `expired`. The gate drives `PROCESSING`, `PENDING`, `SESSION_INITIATED` with a half-finished journey, and a status this adapter has never seen — none of them is recorded as a pass or as a failure — plus the `expired` state, which is.
- **The four documented decisions map honestly.** `PASSED` passes; `REJECTED` fails, with the reason chosen by *which* capability decided — liveness rejected is `liveness_failed`, similarity rejected is `document_mismatch`, a document capability rejected is `document_unreadable`; `WARNING` is `unknown`, because a warning is risk a person must weigh and not a rejection this platform may record; `NOT_EXECUTED` is `unknown` for the same reason. A pass needs the document capabilities, liveness and — when the workflow ran it — similarity all `PASSED`. The gate drives twenty-one records through that mapping, including a visa (which makes no residence claim), an unsupported document, a document type this adapter has never seen, and a decision word Jumio never documents, which is dropped rather than believed.
- **A supplementary pass is never a KYB verdict.** Every answer the adapter can produce is one of STEP 170's five words; the gate asserts, for every record it drives, that the result is not one of the processor's `pending`, `action_required`, `verified`, `restricted`, `rejected`, that `supplementaryIdvOverlapsProcessorKyb` is false, that a hostile record containing `VERIFIED` still fails on its rejection, that `refuseProcessorKybWrite("verified")` is refused, and that the office summary carries `changesProcessorKyb: false`. A pass, a failure, an expiry and a warning all end in STEP 170's manual-review fallback where they should.
- **A result never moves backwards.** A recorded pass cannot be replayed into a failure: the gate records a pass, then replays a rejected liveness against the same session and asserts the recording is refused while the stored pass stays. A second read of the same answer reports `changed: false`.
- **UI** — not applicable: this STEP adds no screen, so no desktop or mobile width was checked. The vendor settings screen is STEP 175's and the merchant's status line reads STEP 170's neutral phrase.
- **Security** — the credential and the delivery secret exist only inside the sealed field and the one Basic header; no request body carries a name, a date of birth, a document number, a document part, an image or a consent record; the redirect URL is never persisted; the token is cached in memory only; every answer is bounded by `JUMIO_MAXIMUM_ANSWER_BYTES`; redirects are refused; the timeout is bounded; and the source is asserted to carry no hard-coded host beyond Jumio's documented ones, no console logging and no `process.env` read.

## Not Run / Open

- **No callback receiver, and no signature verifier.** Jumio's callback is STEP 174's. The callback's signature scheme and header names were **not** established in this session, so this file does not pretend to verify a delivery: it only reads a workflow through the Retrieval API, which is exactly the answer a callback would have to be confirmed against. Nothing here trusts a delivery body.
- **No vendor settings screen.** The screen that lets a super administrator save, test, activate, rotate and retire a Jumio configuration is STEP 175's; this STEP supplies the functions it will call (`createJumioConfiguration`, `activateJumioConfiguration`) and their audit vocabulary.
- **`docs/final/PROVIDER_DOCS.md` was not touched.** That file belongs to STEPs 147-169, and this STEP's ownership is `lib/kyc/adapters/`; rather than write into another STEP's file, the provider facts live in the adapter's header table and in the "Provider documentation read in this session" table above, in the same form that file uses. Whoever owns `PROVIDER_DOCS.md` can lift those two tables across unchanged.
- **This gate is not in the `verify` chain.** `package.json` is a shared file the File Ownership Rules give to the foundation STEPs, and no exception is granted to STEPs 170-175. Running it needs `node lib/kyc/adapters/jumio-verify.ts`.
- **Testing is a mock tenant, not a separate host.** Jumio documents no test datacenter: a sandbox run is a dedicated mock-service tenant on the same three hosts. That mock service chooses its scenario by putting a JSON string in `customerInternalReference`, which this adapter derives from the session id and therefore does not use — a real limitation for end-to-end tests, recorded rather than worked around by letting a caller inject that field.
- **No document is ever uploaded from here.** The person is handed to Jumio's own page; credential upload, prepared data and the finished transaction's images are deliberately not implemented, so no document number, image or biometric enters this platform through this module, and the extraction data in the retrieval payload is discarded apart from the document *kind*.
- **Nothing is persisted, routed or shown.** Both stores are STEP 170's ports with in-memory reference implementations; the session and configuration tables, their RLS, the session-opening route and the refresh job arrive with the STEPs that own them.
- **Manual KYC remains the running mode.** No configuration is active anywhere, so STEP 170's `supplementaryIdvModeOf` still answers `manual` for every company today.
