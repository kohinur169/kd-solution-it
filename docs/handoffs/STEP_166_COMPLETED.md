## Behaviour Proof (acceptance checklist)

- **Section 6, sentence one: the keys are sealed before storage.** `configureAirwallexKeys` validates first and seals second, so an invalid value never becomes an envelope; the client id, the API key and (when given) the webhook signing secret are sealed under three different per-company AES-256-GCM scopes; and the gate asserts the stored record and its JSON never contain any of the three values in clear. A configuration sealed with one keyring cannot be opened with another, and the refusal says so.
- **Section 6, sentence two: a saved key is never shown in full.** `maskAirwallexCredential` keeps the last four characters and nothing else — there is no documented prefix to keep, so no prefix is invented — and a value of eight characters or fewer is hidden entirely. `airwallexKeyViewOf` opens the envelopes only to mask them and returns the masked pair, the masked webhook secret, the host, the pin, the status, the last test outcome with its time, and the last updated time; the surface that will render this screen therefore cannot show what it never receives.
- **Section 6, sentence three: no provider is enabled on a failed test.** Activation reads the record, not a caller's claim. It refuses a retired, already-active, superseded or untested configuration; it refuses one whose last test said anything but `connected`; it refuses one whose test issued a token but never proved it; and it refuses a test made on another version or another host than the stored ones, because that test proved something else. The in-memory store enforces the same rule at the write, so a caller that bypassed `activateAirwallexConfig` still cannot reach `active`.
- **The proof is the two documented calls.** `POST /api/v1/authentication/login` with `x-client-id`/`x-api-key` and no body, then `GET /api/v1/balances/current` with `Authorization: Bearer`. The gate asserts exactly two calls in that order, that the login carries no bearer token, that the read carries no client id and no API key, and that `connected` is impossible without both. Only the balance **count** is kept: the result, the record and the audit entry never carry a currency or an amount.
- **The mode comes from the host, because the key has no prefix.** STEP 165 could not read a credential prefix anywhere, so `configureAirwallexKeys` stores the documented host with the mode and `testAirwallexConnection` refuses a record whose stored host is not the documented host for its environment. The recorded test names the host it proved, which is why activation can refuse a proof made elsewhere; a sandbox key pasted into a live configuration fails at the first call rather than later.
- **The token is never a stored credential.** It lives in `InMemoryAirwallexTokenCache` only, is refreshed one minute before the documented `expires_at`, is cleared when the authenticated read refuses it, and is refused to any configuration that is not `active`. The gate asserts the token appears in the cache and in no record, no view, no result and no audit entry, and that `airwallexAccessTokenFor` reuses a fresh token instead of logging in again.
- **The login answer is read for what it is.** `201` with a `token` and a readable `expires_at` is the only success, with the documented `2021-06-18T16:30:00+0000` shape read to the exact millisecond; `401` is `credentials_rejected` and keeps the documented `credentials_invalid`/`credentials_expired` distinction; `403` is `not_permitted`; `400` is `rejected` unless its code names the version; and `429`, a timeout class, a `5XX`, a redirect, a thrown transport and a `2XX` without a token are all `unknown`, because a token may exist. Nothing is upgraded to a reason it does not have.
- **The version question is answered on evidence, never guessed.** A refusal whose code is `incorrect_version` or `request.api_version_unsupported` is `version_rejected`, and the reason names the pinned value and the candidates. `probeAirwallexApiVersions` then tries the pin and every recorded version **newer** than it — `2026-05-29`, then `2026-08-21`, exactly the pair STEP 165 could not settle — reports which one the account accepted, and **changes nothing**: the gate asserts the stored pin and the record's version are untouched after a probe. At most three candidates are tried and only recorded ones.
- **The webhook signing secret rotates behind the same seal.** Because STEP 165 recorded that Airwallex gives each notification URL its own secret, the roll replaces the value rather than keeping a previous one: the gate asserts a roll to the stored value is refused as "unchanged", a new value is stored sealed, the view shows only its last four characters, the old and new values never appear in the record in clear, and a keyring that cannot open the stored secret cannot rotate it.
- **The transitions keep one active configuration.** Activating a second configuration supersedes the previous one in the same call, in the order the store's invariants allow — supersede first, activate second — so a company never holds two active configurations and a superseded one can never come back. Retirement ends every path: a retired configuration cannot be tested, activated, re-retired or rotated.
- **UI** — not applicable: this STEP adds no screen, so no desktop or mobile width was checked. The settings screen that shows the masked values and runs the test is the admin-provider-key surface the plan assigns to the STEP that owns the route; this STEP supplies the functions it calls and the masked view it renders.
- **Security** — validation runs before sealing (bounds, character sets, an access token or a pasted `x-api-key`/`Bearer` header refused as a field value, the two fields refused when equal, the version refused unless it is a date, the webhook secret refused when short, long or whitespace-bearing); the transport refuses any path outside the two documented ones and any host but the documented one for the stored mode, refuses redirects, bounds the timeout at 15 s and the answer at 64 KiB, and no credential ever reaches a URL; every message is sanitised and bounded; every refusal is a reason, never a value; six audit actions (`provider_key.configured`, `provider_key.tested`, `provider_key.activated`, `provider_key.retired`, `provider_key.rotated`, `provider_webhook_secret.rotated`) carry the provider key, the company, the configuration, the mode, the outcome and the time — and never a credential, a token or a balance. No route, no job and no table, so the pre-existing RLS and permission middleware are untouched.
