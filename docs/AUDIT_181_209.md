# Audit of STEPs 181 to 209 — defects found, gaps either closed or named

Date: 2026-11-07. Branch `arena/ca936761-kd-solution-it`, from `631c0c2` (STEP 209).

The instruction was to check every STEP written in the 181 to 209 range for a defect or a gap and to
repair what is found. This is that record: what the pass looked at, what was wrong, what changed, and
what is honestly still missing. Every fix below is a code change with a gate check behind it; no gate
was loosened to make a failure go away.

The range covers the public store API and its merchant plugin: store payments (`203`), the payment
status read (`204`), store webhook delivery (`205`), test credentials and the sandbox (`206`), the
simulated webhook sender (`207`), and the WooCommerce plugin's connection (`208`) and callback (`209`).

Read this as a companion to `docs/AUDIT_120.md`, which did the same for the earlier range.

---

## 1. Method

1. Re-read the seven STEPs' handoffs and their sections in `docs/final/FEATURE_LIST.md`.
2. For each exported function in `lib/api/store-*.ts`, `lib/api/sandbox-*.ts` and
   `lib/api/payment-fields.ts`, ask who calls it in `lib/` and `app/`, so a seam nothing reaches and a
   name nothing uses both surface.
3. Read the plugin's six PHP files end to end, because the sandbox has no PHP interpreter and no
   WordPress: a source read is the only review those files get.
4. Look for asymmetries between two STEPs that were written three steps apart - a status one refuses
   and the other accepts, a count one hardcoded and the other computed, a store shape one allows and
   the other cannot reach.
5. Re-run the six gates for the range and re-check every new assertion by mutation: a check that still
   passes when the line it names is broken is not a check.

## 2. Defects found and fixed

### 2.1 A revoked connection beside a live one made every shop that moved permanently ambiguous

`lib/api/store-callbacks.ts` refused a callback when the merchant had more than one connection row,
reasoning that a connection names a domain and a payment names no store, so two rows would leave the
platform guessing. But `migrations/0035_store_connections.sql` makes revocation final and never
deletes the row: a merchant who revokes one shop and connects another has exactly two rows for the rest
of the tenant's life, and every callback to the *live* shop would have been refused
`409 connection_ambiguous`.

The refusal now counts **only active rows** for ambiguity, and the reasons are reported in the order a
merchant can act on: none at all (`connection_missing`), one revoked (`connection_revoked`, the final
state 0035 describes), a row that never finished activating (`connection_not_active`). The read also
asks for fifty rows instead of one, and a refusal now actually throws - three branches had awaited the
audit write and returned nothing, so the caller received `undefined` instead of the refusal.

Gate: `verify-store-callback` fixtures `revokedBesideActiveFixture`, `pendingBesideActiveFixture` and
`twoActiveFixture` pin all four answers, including the case that must still be ambiguous.

### 2.2 The plugin could pay the wrong customer's order

`KD_Callback::order_of()` found the order through `wc_get_orders` with a `meta_query` on
`_kd_payment_id`. On a shop using WooCommerce's legacy post storage that argument is silently ignored:
the query returns the newest orders regardless of the meta, so the endpoint would have marked the most
recent order paid on the strength of a callback naming a different payment. This was the single most
dangerous defect in the range, and it fails silently - no error, no log, just the wrong order moved.

The lookup now asks both ways (`meta_query` first, then `meta_key`/`meta_value`, stopping as soon as
one answers) and then **verifies every candidate in PHP** with `get_meta()`, keeping only orders whose
meta really carries the payment id. A wrong answer from the store can no longer become a wrong order.

Gate: five source pins - the key constant, the `get_meta` verification, the empty-candidate guard, and
the absence of a first-result shortcut - plus the pre-existing behaviour pins on the duplicate guard.

### 2.3 The 208 gate could not see the files 209 added

`verify-woocommerce-connection` reviewed "the plugin, file by file" against four hardcoded file names,
so STEP 209's additions were outside the loop that checks the direct-access guard, the delimiters and
the escaping. The list is now a recursive walk of the plugin directory, `.php` only, sorted, with an
assertion that the four files this STEP wrote are among them and that `readme.txt` is not.

The same gate counted `wp_nonce_field` occurrences against the literal `4`. Adding a form to the
settings screen broke the count, and the claim it was making - every form carries a nonce - was never
really being tested. It is now an equality against the number of forms on the screen, so a form added
later must carry a nonce *and* the equality holds.

The same shape was found in the authorise check: it asserted that `$this->authorise()` appeared exactly
four times, which is a fact about the screen today rather than the rule. It is now an equality against
the number of `handle_*` handlers, with a floor of four, so a fifth handler must authorise too.

### 2.4 Nothing let a merchant test the callback path

Step 209 delivered a callback endpoint the platform starts on a request, and the plugin could receive
one, but a merchant had no way to see the path work before a real customer paid - the first exercise of
`wp_remote_post`, the store token and the platform's own re-read would have been the live one.

The plugin's screen now has **Send a test callback**: `KD_Settings::handle_test_callback()` (its own
nonce, its own capability check) asks `KD_Connection::test_callback()`, which finds the newest payment
the shop created through the meta the gateway wrote and asks `KD_Api_Client::request_callback()` to
have the platform call this shop about it. The screen repeats the platform's own `delivered` and `rule`
and nothing else. **Nothing in this path marks an order paid**: only the callback endpoint may, and only
after asking the platform. The readme says so, and the gate pins it.

### 2.5 A shop installed in a subdirectory would have connected to a callback that cannot arrive

The platform derives a shop's callback address from the connection's bare domain
(`https://{domain}/?wc-api=kd_payments_callback`), because `0035` stores a domain and nothing else. A
WordPress installed at `https://example.com/shop/` answers only at
`https://example.com/shop/?wc-api=...`. Such a shop would have connected successfully and then failed
every delivery, with the platform reporting a store failure the merchant could not explain.

`KD_Connection::install_path()` reads the path from `home_url()`, and `connect()` now refuses before it
sends the handshake, in words the merchant can act on. The readme states the requirement. The gate pins
the path read, the refusal, that it comes before the request, and the readme line.

### 2.6 The delivery seam was reachable from nowhere, and nothing guarded it

STEP 205's outbound delivery has no trigger in this range: no code moves a store payment's state yet, so
nothing can schedule an event. That is a gap this range cannot close, and it is named in section 3.
What is *inside* the range is the seam a later STEP calls - `registerStoreWebhookJobOnPlatform()` and
`getStoreWebhookScheduleRuntime()` - and nothing checked that either still existed or that no route
registered the job for itself (which would register it once per request, against a fresh registry).

`verify-store-webhooks` now pins both functions and their wiring to the process-wide queue, and walks
`app/` to assert that no route registers a job of its own. Three mutations confirm it: renaming the
registration helper, detaching the scheduler from the shared queue, and registering a job inside a route
are each caught.

### 2.7 An unused export

`wooCommerceConnectionPath()` in `lib/api/store-connections.ts` had exactly one mention in the tree - its
own definition. Removed, with its import.

## 3. Gaps confirmed as real, and left to the STEP that owns them

These are not defects to patch here: closing any of them would mean inventing a STEP's subject early.

| Gap | Why this range cannot close it | Where it is recorded |
|---|---|---|
| Nothing schedules a webhook when a payment's state changes | no code transitions a store payment yet; the transition and the fulfilment it implies belong to a later STEP | `docs/handoffs/STEP_205_COMPLETED.md`, this document |
| Nothing schedules a callback when a payment's state changes | same absence; the callback re-reads the payment, so the shop's order moves only when the platform's status does | `docs/handoffs/STEP_209_COMPLETED.md` |
| The job is never registered at platform boot | the queue and worker foundation is STEP 011's, and a later STEP must not alter it; the seam is pinned so that STEP has one call to make | this document, section 2.6 |
| The plugin has never run | there is no PHP interpreter and no WordPress in the sandbox; the gates check source text, delimiter balance and the invariants a source read can prove, and nothing here claims execution | `docs/handoffs/STEP_209_COMPLETED.md` |
| No buyer checkout page for API-created payments | the store's own checkout is the buyer's page; a platform-hosted one is another STEP's subject | `docs/handoffs/STEP_209_COMPLETED.md` |
| One connection per tenant, with no screen to choose | `0035` allows one active row per `(company, platform, domain)`, and a payment names no store, which is why the callback read refuses two active rows rather than guessing | `docs/handoffs/STEP_209_COMPLETED.md` |
| A revoked connection can never be reinstalled through the public API | `0035` makes revocation final; reinstalling is a support action, and the endpoint says so rather than silently reactivating | `docs/handoffs/STEP_208_COMPLETED.md` |
| A webhook and a callback both fire for one payment | they are different transports with different credentials, and the message in each says the same thing; whether to deduplicate them is a decision no STEP has taken | `docs/handoffs/STEP_209_COMPLETED.md` |
